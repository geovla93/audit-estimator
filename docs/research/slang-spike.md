# Slang parser and binding capability spike

**Plan 002 research is complete.** The parser is usable in this Node ESM project for the tested syntax and source locations when the research decoder provides a BOM-free parser view. Semantic binding supplies exact source locations for many edges, but alias and overload results remain candidate sets; unresolved edges stay unknown. This spike changes no production parser, metric, or estimator behavior. The approved leading-BOM decoder exists only in `test/research/slang-source-view.ts`; Plan 006 must implement and review the production adapter separately.

## Package, API, and runtime evidence

The exact runtime dependency is `@nomicfoundation/slang@1.3.9`, the stable release selected on 2026-10-14. Its package manifest declares MIT, ESM exports for the root package and `parser`, `cst`, `ast`, `utils`, `compilation`, and `bindings` subpaths, one runtime dependency (`@bytecodealliance/preview2-shim`), four `.wasm` assets, and no `engines` or lifecycle `scripts` fields. The generated package wrappers load on Node `24.21.0` / Darwin arm64 without native compilation or lifecycle scripts. Frozen lockfile installation passed before and after adding Slang.

The spike directly exercised `Parser.create`, `Parser.languageVersion`, `parseFileContents`, `ParseOutput.isValid`, `ParseOutput.errors`, `ParseOutput.tree.unparse`, `LanguageFacts.earliestVersion`, `latestVersion`, `allVersions`, and `inferLanguageVersions`; cursor traversal, terminal trivia, `TextRange`, typed `SourceUnit` / `ContractDefinition` / `InterfaceDefinition` / `ErrorDefinition` / `LibraryDefinition` / `StateVariableDefinition`; `CompilationBuilder` callbacks; and `CompilationUnit.bindingGraph` with definition and reference locations. The API usage follows the [Slang parser guide](https://nomicfoundation.github.io/slang/latest/user-guide/05-syntax-trees/01-parsing-source-code/), [AST guide](https://nomicfoundation.github.io/slang/latest/user-guide/05-syntax-trees/04-using-ast-types/), [syntax-error guide](https://nomicfoundation.github.io/slang/latest/user-guide/05-syntax-trees/02-handling-syntax-errors/), and [binding graph guide](https://nomicfoundation.github.io/slang/latest/user-guide/07-semantic-analysis/02-binding-graph/).

Therefore no-pragma selection still needs an explicit policy; inference alone cannot choose a compiler grammar.

## Parser views, BOM handling, and source locations

The raw parser evidence remains useful: parsing `test/fixtures/parser/bom-locations.sol` directly produces one whole-input diagnostic, from UTF-8 offset 0 / UTF-16 offset 0 / line 0 column 0 through UTF-8 60 / UTF-16 58 / line 2 column 0. The raw tree's `unparse()` omits the first three BOM bytes, returning 57 bytes from the original 60-byte fixture. The raw-parser regression remains separate from the adapter capability test.

The approved test-only decoder records a copy of the original bytes, decodes UTF-8 with fatal error handling while preserving U+FEFF, detects exactly one initial UTF-8 BOM (`EF BB BF`), and removes that one character only from parser, pragma-inference, and compilation-callback views. It does not alter the recorded original text or bytes. It preserves interior and repeated BOMs. It rejects invalid UTF-8 instead of replacing malformed bytes. After valid parsing, the harness prepends the recorded BOM to `tree.unparse()` and compares the result byte-for-byte with the original. Hashes are computed from original bytes; the BOM fixture asserts the original-byte hash differs from the parser-view hash.

For any parser range endpoint with a leading BOM, the harness maps back to original coordinates by adding 3 to UTF-8 offset and 1 to UTF-16 offset, retaining the line, and adding 1 to the column only on line 0. Without a BOM the range is unchanged. This mapping was checked against Slang's observed column convention: columns count Unicode scalar values, not UTF-16 code units. For `/* 🙂 */ contract C {}`, the parser reports `C` at UTF-8 20, UTF-16 18, line 0 column 17; with an initial BOM the mapped start is UTF-8 23, UTF-16 19, line 0 column 18. A BOM-prefixed malformed `contract` reports parser-view EOF at 8/8, line 0 column 8 and maps to original EOF at 11/9, line 0 column 9. The BOM-only case also reconstructs exactly.

The combined BOM + CRLF + π/emoji fixture verifies a later-line identifier: UTF-8/UTF-16 offsets map to the original text, line 2 and column 9 remain unchanged, and reattachment restores exact bytes. The CRLF fixture verifies exact text reconstruction, trivia, and distinct UTF-8/UTF-16 offsets around Unicode. Slang's `TextIndex` also counts CR, LF, and CRLF lines correctly. Its range index advances across U+2028 and U+2029, but Slang 1.3.9 rejects those characters as separators between top-level declarations; the resulting error range ends at line 1 column 13. That syntax remains unsupported by this fixture and must not be silently normalized.

This decoder and offset mapping are research evidence, not a production parser adapter. Any production application must preserve the original bytes for fingerprints and physical accounting, use the parser view only for syntax/pragma/import callbacks, map diagnostics and all range endpoints back, and restore original bytes for any reconstruction used to prove source fidelity.

No production global resolver or name-only fallback is justified by this spike.

## ESM isolation, transfer, and resource observations

The trusted harness builds `test/research/slang-child.ts` as plain ESM into ignored `.vitest/research/slang-child.mjs`, with Slang external to the bundle. A plain Node `24.21.0` child imports Slang and its WASM assets without loaders, environment hooks, or target code. The test removes `NODE_OPTIONS` and `NODE_PATH`, applies `--max-old-space-size=64`, sends malformed input followed by valid input, handles repeated batches, and exits cleanly. A synchronous `Atomics.wait` stall is acknowledged by the child; the parent deadline fires after 350 ms, kills and reaps the child, and confirms no child PID remains. This proves process termination for the tested child, not a portable hard wall-clock or RSS guarantee.

`JSON.stringify({ parser, output })` produced 25 bytes, and the rehydrated parse output had no `isValid` method. `structuredClone(output)` returned a plain object. This directly tests loss of the `ParseOutput` API through ordinary serialization/cloning; it does not individually test every parser, CST, AST, cursor, or binding object. A worker boundary should flatten the specific records it needs inside the child and test that transfer contract.

One advisory measurement run in a fresh child gave:

| Synthetic source and parses   | Source bytes |  Elapsed | Heap-used delta |     RSS delta | Array-buffer delta |
| ----------------------------- | -----------: | -------: | --------------: | ------------: | -----------------: |
| 100 declarations × 3 parses   |        1,837 |  22.3 ms |      +229,528 B | +53,510,144 B |           +5,529 B |
| 5,000 declarations × 2 parses |       98,937 | 181.7 ms |      +119,088 B |  +9,388,032 B |         +197,886 B |

These are single-run advisory samples, not thresholds or canonical benchmark results. Startup allocation, WASM memory, and garbage collection make the deltas non-comparable. V8's `--max-old-space-size` limits the JavaScript heap; it does not hard-cap WASM linear memory or process RSS.

For Plans 004 and 006, use their proposed operational limits as the starting design: 2 MiB per source file, 64 MiB total source, 2,000 discovered files, a 2-second per-file parse deadline, a 10-second semantic-component deadline capped at 128 files / 8 MiB, and child recycling after 32 files or 8 MiB. The 64 MiB JavaScript heap used in this spike is an experiment setting, not a proven production limit. The supervisor can kill the child on deadline, but this spike proves no hard RSS ceiling; that requires OS-level resource controls. The small synthetic samples do not validate these limits. Keep limits configurable only through reviewed application policy, not target-project configuration.

## Verification and maintenance

The spike suite asserts behavior rather than snapshots. The full fixture and capability tests are in `test/research/slang-spike.test.ts`; the decoder is in `test/research/slang-source-view.ts`. Rerun the fixture, semantic, and child-isolation matrix on every Slang upgrade, including patch upgrades. Add a fixture before making a new syntax or binding claim. Keep parser errors, candidate sets, unresolved edges, and compiler validity as distinct states.
