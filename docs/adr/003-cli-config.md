# ADR 003: Predictable commands and data-only configuration

Status: accepted for Plan 004, 2026-10-15.

## Decision

The command surface is a local Commander 15 program created by `createProgram(handler, io)`. Each invocation owns its command instances and receives an injected handler and output streams; reusable CLI code does not call `process.exit`. The executable shim sets `process.exitCode`. `estimate`, `inspect`, and `explain` each require exactly one input path. `explain` marks the request for breakdown presentation. The shim connects the analysis handler from `createAnalysisHandler`, owns one `AbortController` that its first `SIGINT` aborts (a second `SIGINT` falls through to Node's default termination), and ignores a closed output pipe without a stack trace. In JSON mode stdout receives exactly one report envelope, including for usage errors (the final `--format json` or `--format=json` is pre-scanned from argv); human-readable diagnostics are one sanitized `CODE: message` line each on stderr. Format precedence is CLI `--format`, then config `report.format`, then terminal. Color requires terminal format, no `--output`, no `--no-color`, and a TTY stdout; environment variables are never consulted.

All subcommands accept `--include <glob>` and `--exclude <glob>` (repeatable), `--root <path>`, `--config <file>`, `--no-config`, `--format <terminal|json|markdown>`, `--output <file>`, `--force`, `--solidity-version <exact>`, `--allow-partial`, `--strict`, and `--no-color`. Glob options take one value per occurrence; comma-separated lists are not split. Repeated scalar options use Commander’s last value. `--force` requires `--output`; `--config` conflicts with `--no-config`. Unspecified options remain absent in the normalized request so they do not override configuration. Unknown options, extra arguments, invalid formats and inexact Solidity versions are usage errors. Help and version exit without invoking the handler.

The selected root is explicit `--root`, otherwise the directory input, or the parent of a file input. Root and input are canonicalized and an explicit root must physically contain the selected input. Only `audit-estimator.config.json` directly under that root is auto-loaded. There is no parent-directory or home search. Explicit `--config` paths and CLI `--root`/`--output` paths are resolved against the process working directory. Config path values are resolved against the config file's directory, then normalized to project-relative POSIX paths. Existing path components are checked through their physical resolution, including symlinks; later discovery repeats confinement checks before opening files to handle filesystem changes after configuration loading.

Configuration is bounded UTF-8 JSON data at schema version `1.1.0` (files declaring the previous `1.0.0` stay valid through their strict legacy shape), capped at 256 KiB. The `estimationScope` selectors are a deliberate exception to config-directory-relative paths: they are project-root-relative canonical paths that are only matched against the final accepted scope manifest, never rebased, resolved through symlinks from the config directory or added to discovery, so the same selection behaves identically from a root, nested or external config and from the library request. The loader uses a nonblocking, no-follow open and verifies the opened descriptor is a regular file before reading a bounded number of bytes. Automatic config symlinks are rejected. An operator-selected explicit config symlink is followed to one resolved file; that file can include no other files, and its source roots, import remappings and coverage path must still remain physically inside the selected project root. File contents, parser diagnostics, filesystem paths and unexpected causes are not copied into public errors. JavaScript/TypeScript, YAML, environment interpolation, schema fetching, upward search, dynamic imports, executable names, module paths and network endpoints are not configuration inputs.

The precedence order is trusted defaults, validated supplied metadata hints, validated file config, then explicitly present CLI values. Plan 005 may supply Foundry metadata as plain validated input; this layer performs no metadata I/O. Every provided layer is validated before merging, including values later replaced by another layer. Scalars replace prior values, arrays replace rather than append, and recognized nested records merge field by field. Unknown and prototype-like keys are rejected. Config-relative source, third-party, first-party override, remapping context/target and coverage paths are root-confined. `firstPartyOverrides` is the deliberate ownership-promotion rule; includes can widen selection, but cannot disable exclusions or safety checks or change ownership by themselves.

Default exclusions remain a separate built-in set enabled by `scope.defaultExcludes`; explicit excludes do not replace them. Supported globs use root-relative POSIX paths, literal path segments, standalone `**`, `?`, and at most one `*` in another segment. Negation, braces, extglobs, character classes, backslashes, absolute paths, drive paths, empty segments and `.`/`..` segments are invalid. List length/count and a per-run `maxGlobStates` budget bound synchronous matching work. Operational analysis limits are distinct from model settings, exposed in the resolved config, positive, finite and capped at ten times their baseline (with a 600,000 ms duration ceiling).

The complete `heuristic-v1` model profile is injected by a trusted caller. This plan defines no model coefficients; the project-config layer only validates and merges explicitly supplied model fields. Defaults therefore cannot be mistaken for a calibrated profile or guessed placeholder values. Field provenance records `default`, `metadata`, `config` or `cli`, sorted by Unicode code point. The semantic hash includes effective model, scope, imports, Solidity, limits, manual adjustments, coverage, and enabled default exclusions. It excludes report format and provenance, which cannot change analysis semantics.

Exit statuses are stable: 0 complete, 1 internal error, 2 usage/configuration error, 3 unreadable target or empty scope, 4 partial/unsupported/limited result or strict warning, 5 output failure, and 130 interruption. A strict warning cannot mask an internal, configuration, target or output failure. Allowing partial work never changes an incomplete result to status 0. Reusable code returns status values; only the executable shim updates `process.exitCode`.

`--output` writes only after the full report body is rendered and validated. The destination's parent directory must already exist and is never created. The writer refuses a `.sol` destination, any path or `(device, inode)` identity that matches a source, configuration, metadata or coverage file the analysis read (so hardlinks are caught), an existing symlink, and an existing non-regular file. Without `--force` the file is created with `O_CREAT | O_EXCL`, so there is no check-then-write window. With `--force` an existing regular file is opened with `O_NOFOLLOW` where the platform provides it and without `O_TRUNC`; the opened handle is verified as a regular, unprotected file before it is truncated and written. After a write failure the writer unlinks only a file it created in the same call, proven by matching `(device, inode)`, and never unlinks a pre-existing file. A report that is an error envelope is not written to the file. On a write failure the exit status is 5: JSON mode prints the output-failure error envelope on stdout and other formats print one stderr line. A concurrent attacker able to mutate the destination directory between verification and write is outside this guarantee, consistent with the race statement in ADR 004; rename-based writes are not claimed to give atomic no-clobber on every platform.

## Consequences

CLI syntax and configuration resolution stay independent of parsing and estimation. The config resolver returns validated domain settings, provenance and a deterministic semantic hash, but does not discover or analyze sources. Output format and destination are presentation concerns. Plan 013 may connect these contracts to analysis without changing flag precedence or permitting project-provided code execution. Adding a config field, format, environment source, executable hook or glob feature requires a schema, validation, help, documentation and test update together. A change to model coefficients belongs to Plan 010.
