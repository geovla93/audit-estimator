# ADR 002: Plain domain contracts and versioned JSON

Status: accepted for Plan 003, 2026-10-14.

## Decision

The parser adapter, discovery layer and estimator exchange plain, serializable records. `src/domain/types.ts` defines readonly TypeScript DTOs; `src/domain/schemas.ts` validates their runtime form with Zod 4. The domain does not import Slang, filesystem or terminal APIs. `SourceSnapshot` and source-line sets are internal only; reports contain no source bytes, source text, native absolute paths, parser cursors, `BigInt`, timestamps or stack traces. The public library entry exports `analyzeProject`, pure estimator/model APIs, report renderers, domain types and version declarations; parser, discovery, relationship and indicator internals are not public deep-import APIs.

File IDs derive from a normalized project-relative POSIX path, using canonical physical identity to deduplicate symlink aliases. Byte hashes describe content and never deduplicate files. Contract and callable IDs add declaration kind and the start byte offset; edge IDs add an ordinal. Equal short names therefore remain distinct. The discovery layer must resolve root confinement and physical identity before constructing these IDs. Public paths and physical identities are root-relative POSIX strings. Windows separators normalize at the canonical identity boundary; native absolute paths remain in the internal load context.

`EvidenceRef` names a file and a zero-based, half-open UTF-8 byte range in the **original** source. Presented line and column are one-based; columns count Unicode scalars. Plan 002 established a narrow parser-view removal of one leading UTF-8 BOM and the exact map back to original coordinates. Plan 006 must apply that map before producing these records. New evidence coordinate semantics require a metrics-version review. A measured zero means observed absence; `unavailable` carries a reason and never becomes zero. Ownership (`first-party`, `third-party`, `unknown`) is independent from scope role (`scoped`, `context`, `excluded`). Unknown ownership is retained with evidence and must not imply a security conclusion.

Metrics version `1.0.0` identifies these count definitions, whose extraction belongs to Plan 007: physical lines split CRLF/LF/CR with no terminal empty segment; source lines are unique lines intersecting non-trivia Solidity or Yul tokens; contract lines can overlap, while project totals use unions of unique scoped file lines. Decisions count syntactic `if`, ternary, loop, catch and logical operators in callable bodies; loops and depth are separately explanatory. Yul statement/call/control counts are distinct from Solidity decisions. State variable counts distinguish declared and mutable variables, and syntactic complex shapes from resolved types. Candidate low-level syntax is distinct from confirmed builtin calls. Unsupported syntax, failed binding and unknown type classification use `unavailable`. Versioned report fields retain the measurement status and evidence; none of these counts claims compiler-level control flow or storage layout.

`ConfigInput` is data-only, with current version `1.1.0` (the earlier `1.0.0` shape is still accepted as a strict legacy input without `estimationScope`), strict known keys, bounded arrays/strings/numbers and a 256 KiB byte cap before JSON parsing. `ConfigInputSchema` rejects prototype-like keys recursively before its strict Zod object parser; `parseConfigBytes` also enforces the byte cap and fatal UTF-8 decoding. Scalars replace earlier layers, arrays replace rather than concatenate, and absent CLI values do not overwrite config. `ResolvedConfig` records field provenance (`default`, `metadata`, `config`, `cli`) and expanded logical root-relative settings. Native root/config paths are internal. Remapping targets remain root-confined. Operational limits are positive integers and are separate from estimator parameters. Output destination, force and color are presentation options, never model weights.

The sole reserved model ID is `heuristic-v1`, labelled **uncalibrated heuristic**, with versions `1.0.0` (frozen, physical full review) and `1.1.0` (default; the [amendment](../model/heuristic-v1-1.md) changes which declarations require full review, not any coefficient). This contract reserves the parameter names and units but no coefficients. Plan 010 supplies reviewed values and methodology. Seven low/high pairs cover project hours, SLOC hours, three premiums, interaction hours and boundary hours; `unknownReserveHigh` and `hoursPerDay` are scalars. Profile numbers are finite, ordered, six-decimal values within the bounds in Plan 010. Manual adjustments have unique IDs, nonempty reasons and ordered signed hour ranges; negative values are explicit discounts. The application converts syntax completeness and required-analysis omissions before constructing engine input; `EstimateInput` retains measurement tags, unknown semantics, eligible files and directed scoped/context pairs. A→B and B→A are distinct; duplicate directed pairs across the two partitions are rejected. Incomplete required analysis has no ordinary full-scope estimate. An explicit partial estimate is labelled `analyzed-subset`; a wide uncertainty range cannot substitute for missing code.

Every report has schema version, tool/command/status, independent parser/metrics/indicators/model versions, fingerprints, scope, nullable analysis and estimates, diagnostics and limitations. Error reports require a stable failure category plus at least one diagnostic and have null analysis/estimates. Complete reports require complete required analysis. Partial reports have no full-scope estimate, and any attached estimate has `analyzed-subset` coverage. A full-scope estimate always has `full` coverage. Diagnostics are bounded structured data with stable codes, severity and phase. No exit-code mapping is frozen here.

## Compatibility and schema generation

The producer validates exact `1.1.0` strict schemas (the additive `1.1.0` revision adds the optional `analysis.estimationScope` metadata); `1.0.0` reports remain readable by consumers. Readers reject an unknown major but may accept additive `1.x` fields and diagnostic codes; `parseConsumerEnvelope` checks the stable core without using the strict producer schema for forward reads. Additive fields/codes call for a minor version. Changed meaning, type or removal call for a major version. Report, metrics, indicators and model versions are reviewed independently. A parser upgrade also changes the analysis fingerprint and triggers metric-version review. npm package `0.x` does not change JSON schema compatibility.

`pnpm schemas:generate` and `pnpm schemas:check` first build the production entries, then the trusted generator bundles the domain schemas into an ignored temporary ESM directory. The generator calls Zod's Draft 2020-12 exporter with unsupported nodes set to throw. It sorts object keys by Unicode code point and writes deterministic pretty JSON. The check compares generated bytes in memory and never writes committed schemas. `$id` values are local URNs; report parsing never fetches a schema. `tsdown.config.ts` uses the production entry points `index`, `bin` and `parser/worker`; shared `analyze` and `version-policy` outputs are verified by the integration artifact inventory.

Zod JSON Schema expresses the structural, type, length, regex and numeric limits, including the non-whitespace manual reason and the status-specific target shape of imports and relationships. Resolved imports and uniquely resolved relationships require targets; unresolved or unsupported records cannot claim one, and ambiguous records require candidates. Cross-field rules such as ordered ranges, duplicate IDs, prototype-key rejection, required completeness and report coverage invariants are additional **runtime** checks; Draft 2020-12 consumers must not claim those checks are encoded by the generated documents. Validation changes require regeneration, fixture review and compatible-version review. The complete, partial and error fixture files exercise both serialization and runtime validation; `test/unit/domain.test.ts` also checks invalid inputs and forward-reader behavior.
