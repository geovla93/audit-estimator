## Solidity parsing

Slang supplies a CST retaining trivia and typed AST views. That makes it suitable for both comment-aware line metrics and declaration/control-flow traversal. Its semantic compilation API uses caller-provided file/import callbacks; local reads can remain under the estimator's control. See [Slang overview](https://nomicfoundation.github.io/slang/latest/), [AST views](https://nomicfoundation.github.io/slang/latest/user-guide/05-syntax-trees/04-using-ast-types/), and [compilation units](https://nomicfoundation.github.io/slang/latest/user-guide/07-semantic-analysis/01-compilation-units/).

The [version selection guide](https://nomicfoundation.github.io/slang/latest/user-guide/04-getting-started/02-choosing-a-solidity-version/) documents `LanguageFacts.allVersions()` and pragma-compatible version inference, beginning at Solidity 0.4.11. **Do not copy its example latest version as a compatibility promise.** The retrieved [upstream releases](https://github.com/NomicFoundation/slang/releases) listed 1.3.8, and 1.3.7 added Solidity 0.8.36. Treat 1.3.8 as the initial spike candidate; verify registry stability/engines and query the installed API before selecting a production pin. No claim that all subsequent compiler versions are supported.

The [error guide](https://nomicfoundation.github.io/slang/latest/user-guide/05-syntax-trees/02-handling-syntax-errors/) describes location-bearing diagnostics and recovery nodes. Recovered trees must not be silently treated as complete metrics. The [binding guide](https://nomicfoundation.github.io/slang/latest/user-guide/07-semantic-analysis/02-binding-graph/) describes lazy graph construction and definition/reference lookup; this is useful capability, not evidence of exhaustive overload, runtime-target, or storage-alias resolution.

The [versioning policy](https://nomicfoundation.github.io/slang/latest/user-guide/09-appendix/01-slang-versioning-policy/) warns that language support changes can affect CST kinds on minor updates. Pin exactly and review fixtures for every update. The [memory appendix](https://nomicfoundation.github.io/slang/latest/user-guide/09-appendix/02-slang-memory-management/) explains WASM resources and nondeterministic finalizer timing. Avoid retained cursors in public records and recycle isolated parser processes. [Node worker documentation](https://nodejs.org/api/worker_threads.html#new-workerfilename-options) says resource limits cover JavaScript engine memory rather than external allocations; a worker-thread heap limit is insufficient as a hard WASM memory guarantee.

Alternative: [@solidity-parser/parser](https://github.com/solidity-parser/parser) offers ANTLR-based AST traversal, locations/ranges and tolerant parsing. It would simplify some visitors, but the chosen approach benefits more from Slang's version APIs, trivia fidelity, and binding interface. No evidence justifies shipping two parsers. Solidity [compiler AST/standard JSON](https://docs.soliditylang.org/en/latest/using-the-compiler.html#compiler-input-and-output-json-description) offers deeper compiler semantics but requires compiler-version availability, import/build configuration, extra runtime weight and safeguards. Optional differential testing of a preinstalled trusted compiler is future work, not an MVP execution requirement.

## Runtime and toolchain

- [Node release schedule](https://github.com/nodejs/Release/blob/main/schedule.json): Node 22 and 24 are LTS lines on the research date; Node 20 is out of support, Node 26 LTS is scheduled later in October. User-confirmed support is Node 24.11+ only for development, CI and runtime (`>=24.11.0 <25`); other maintained majors are outside this project's support scope. Review at release time.
- [Commander source](https://github.com/tj/commander.js) and [manifest](https://raw.githubusercontent.com/tj/commander.js/master/package.json): stable 15 is native ESM with a Node 22.12+ floor. Prefer it over oclif's plugin/application machinery; native argument parsing would require bespoke help, command and error behavior. This comparison is an architectural judgment, not a measured benchmark.
- [Zod JSON Schema](https://zod.dev/json-schema): conversion supports strict object schemas. Prefer Zod 4 for one validation/type/schema contract; AJV would be reasonable for JSON-Schema-first development but adds a separate type-generation workflow here. Export serialization-compatible schemas without transformations.
- [Picomatch](https://github.com/micromatch/picomatch): path matcher rather than filesystem walker. Choose a restricted glob grammar and explicit bounded traversal rather than duplicating traversal controls in a glob package. Do not interpret its performance claims as this project's benchmark.
- [smol-toml](https://github.com/squirrelchat/smol-toml): small TOML parser; validate only recognized Foundry fields after parsing. No TOML expression execution or global Foundry configuration lookup.
- [TypeScript module options](https://www.typescriptlang.org/docs/handbook/modules/guides/choosing-compiler-options.html): the user selected TS7 for no-emit typechecking, ESNext/bundler resolution, explicit `.ts` source imports and strict additional checks. The original NodeNext/tsc-emission proposal is superseded.
- [tsdown](https://tsdown.dev/guide/getting-started) is user-selected for ESM compilation and bundling. Keep runtime dependencies external, including Slang/WASM; use explicit CLI/library/worker entries, source maps, no minification and engine-derived target. [Declaration docs](https://tsdown.dev/options/dts) describe Oxc generation with user-approved `isolatedDeclarations`; verify emitted declarations with TS7.
- [Vitest](https://vitest.dev/guide/) with V8 coverage is approved. `pnpm test` and `pnpm test:coverage` run only source units without builds; `pnpm test:integration` builds first for integration/E2E/research; `pnpm test:all` runs both groups. All tests live under `test/`, outside `src`. Never discover test config in analyzed projects.
- [Oxlint type-aware linting](https://oxc.rs/docs/guide/usage/linter/type-aware) with oxlint-tsgolint and [Oxfmt](https://oxc.rs/docs/guide/usage/formatter) replace the original Biome proposal. Type-aware linting complements the TS7 typecheck gate.
- [pnpm](https://pnpm.io/installation) is approved with exact reviewed stable direct dependency/package-manager pins. Use the selected release's documented local settings syntax; review and narrowly allowlist necessary build scripts.

## Project formats and metric interpretation

[Foundry configuration](https://www.getfoundry.sh/config/index.html) and its [configuration source](https://github.com/foundry-rs/foundry/blob/master/crates/config/README.md) show configurable roots/profiles/remappings. MVP reads only local `profile.default` data and `remappings.txt`; it does not emulate environment/global/profile merging or autodetect every remapping. Missing cases produce instructions for explicit estimator configuration.

[Hardhat configuration](https://hardhat.org/docs/reference/configuration#path-configuration) defines a conventional `contracts` source path but permits overrides. Detecting a Hardhat marker therefore supports conventions only; importing the config is unnecessary execution. [Solidity path resolution](https://docs.soliditylang.org/en/latest/path-resolution.html) distinguishes source-unit names from host filesystem paths and contextual remappings; implement a documented local subset, not a claim of exact solc equivalence.

[Solidity grammar](https://docs.soliditylang.org/en/latest/grammar.html) and [contracts/inheritance](https://docs.soliditylang.org/en/latest/contracts.html#inheritance) are references for syntax and inheritance test design. They do not imply that parsing proves compilation or runtime behavior. Decisions/loops/assembly/state declarations can be measured syntactically; access intent, target dispatch, business invariants, economic correctness and storage alias effects cannot be certified from syntax alone.

## Estimation research and calibration

Compare four starting approaches: pure SLOC productivity (simple but omits context); COCOMO-like parametric models (size plus cost drivers, with coefficients trained for software development); analogy from completed audits (requires matched historical scope and effort); additive expert work breakdown (transparent and usable without a fitted dataset). Choose work breakdown plus bounded, nonoverlapping complexity channels for MVP. **This recommendation is an inference about this tool's constraints**, not an empirical conclusion from security-audit data.

The original study [Negative Results for Software Effort Estimation](https://arxiv.org/abs/1609.05563) compares parametric and analogy methods on COCOMO-style datasets and stresses suitable input data. [Estimating software project effort using analogies](https://bura.brunel.ac.uk/handle/2438/1101) supports analogy as an approach using historical projects. Neither establishes smart-contract-audit coefficients or validates this estimator. Do not borrow development person-month constants.

[OpenZeppelin audit readiness](https://learn.openzeppelin.com/security-audits/readiness-guide) discusses scope and how tests/documentation inform review. A public [GEB audit report](https://www.openzeppelin.com/news/geb-protocol-audit) names three auditors and four weeks, but gives no phase-level actual hours/utilization. This is **insufficient matched ground truth** for converting dates into exact effort. The searched sources did not establish a reusable audit-effort benchmark dataset; this does not prove no such dataset exists.

Future calibration should collect consented frozen scope, exact metric/model versions, actual cumulative hours by phase, team review policy, exclusions/dependencies, novelty/context, and re-review effort. Deduplicate protocol families, split by project/family and time, compare against SLOC-only and expert baselines, report absolute error, signed bias, interval coverage/width and subgroup failures on held-out audits. Fit few identifiable coefficients under nonnegative constraints, investigate residuals before adding features, and publish provenance/licensing before distributing data. The detailed protocol and starter formula are in plan 010.

## Distribution

[npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) supports OIDC and documents npm/Node version requirements. Plan a protected, maintainer-triggered release, pinned actions, read-only PR checks and no long-lived publish token by default. Initial package creation/account setup needs a maintainer, and local dry-run/packing cannot prove remote publishing authorization. [npm provenance](https://docs.npmjs.com/generating-provenance-statements/) supplies release-origin evidence; it is not a security guarantee for dependency behavior. No publishing is authorized by this planning package.
